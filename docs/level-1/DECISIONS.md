# Architectural & Product Decisions

1. **Next.js App Router over Streamlit**: Streamlit served as an excellent rapid prototype for validating the domain model. Next.js is chosen for Level 1 to provide a robust, concurrent, secure, and highly customizable UI for real users.
2. **Server Actions**: We chose Server Actions to ensure critical transaction steps (claiming, renting) happen server-side, enabling atomic database operations without exposing complex client-side state management.
3. **Supabase**: Selected as the Backend-as-a-Service to rapidly deliver PostgreSQL, Auth, and Storage. RLS natively solves complex multi-tenant data access (Warden vs Student).
4. **Simulated Sandbox Economy**: For Level 1, we explicitly remain in a "sandbox" for payments. Integrating a real payment gateway (Razorpay/Stripe) introduces massive scope and regulatory overhead. The UX will clearly label wallet balances as "Simulated" or "Sandbox".
5. **Deterministic Testing Clock**: The auction depends heavily on time. For testing, we inject a deterministic clock into the engine, avoiding flaky tests based on real `Date.now()`. In production, it will use real UTC time.
6. **No-Dues as a Workflow**: The No-Dues interface is an isolated feature in RIO. It does not integrate with actual university infrastructure yet (Level 2/3 target). It serves to demonstrate the capability to Wardens.
7. **Real clock, no override (supersedes 5 for runtime)**: Level 1 prices and deadlines always use real UTC time; tests inject time explicitly and demo data is seeded relative to "now". No user-facing clock control exists, so nobody can manipulate prices.
8. **Forward migrations**: the two original migrations are kept unchanged; five new versioned migrations evolve the schema (paise money, private profile data, ledger, tokens, RLS), migrating existing rows rather than recreating the database.
9. **Database-enforced business rules**: every money-moving or state-changing operation is a `SECURITY DEFINER` Postgres function with row locks, explicit state checks and idempotent ledger keys. Clients have no direct write access to financial tables. Server Actions only validate input and call these functions as the signed-in user.
10. **No service-role key at runtime**: it is used only by the guarded demo seed script.
11. **PGlite for database tests**: the migrations and RLS policies are executed in an in-process Postgres (PGlite) with a Supabase shim, so policy tests run in `npm test` without Docker. A live-Supabase suite covers what PGlite can't (true concurrency).
13. **Public browsing, protected actions**: the marketplace, item pages and all content pages are open without an account; listing, saving, claiming, renting, handover and operations screens need one. The policy lives in one module (`src/lib/auth/route-policy.ts`) and is only the first gate; pages and the database re-check.
14. **Linear price curve**: the Streamlit prototype exposed an `alpha` curve parameter with a default of 1 (linear). Level 1 implements the linear default only, in both TypeScript and SQL, pinned by shared fixtures. Any other curve is a product decision that must change the fixtures first.
15. **Rental and damage figures are proposals**: 2/10/25% rent, 20% deposit, 50% rent-to-own credit and the 25% damage cap come from the prototype. The Terms page labels them as proposed until a campus policy owner confirms them.
12. **Integer paise with half-up rounding**, prices clamped to the floor after rounding (see BUSINESS_RULES.md).
